# State of types in Ruby — тезисный план доклада

Формат: по примеру Highload (название + описание + поминутный план, 30 минут).
Зелёным (🟢) помечены спорные темы для программного комитета.

## 1. Название

State of types in Ruby

## 2. Описание

Каждый рубист это знает: документацию писать лень, сигнатуры отдельно держать лень,
код замусоривать тоже не хочется. В итоге не пишется ничего, а комментарии врут.
В докладе разберёмся с самого начала: что вообще такое типы и зачем они нужны,
если есть тесты. Потом обсудим два известных спора. Первый — дядя Боб говорит,
что при полном покрытии тестами типы не нужны. Второй — Мацумото специально вынес
RBS в отдельную библиотеку, а не встроил в язык. Дальше посмотрим, как всё это
уживается в руби: YARD, RBS, Sorbet. Поговорим про типы и объектный стиль: правда ли,
что в ООП про тип можно не думать, потому что за всё отвечает реализация.
Потом быстро пройдёмся по библиотекам, включая dry-стек как отдельный слой
рантайм-типов. А в конце покажу docscribe: он сам пишет документацию по коду,
умеет брать типы не из кода, а например из schema.rb, и встраивается в проверки
на CI. После доклада будет понятно, когда типы реально окупаются и с чего начать,
чтобы не утонуть.

## 3. Поминутный план

### 1 минута — кто я

Меня зовут Даниил, вот мой гитхаб (github.com/unurgunite). Я поддерживаю docscribe
и ещё несколько руби-инструментов: irb-autosuggestions, rubocop-плагин,
arfi. Организация FlorexLabs — это просто моя папка для своих проектов.
Типами занялся по простой причине: устал вручную чинить протухшие комментарии.

### 2 минуты — пример из жизни (хук)

Метод с параметрами, где комментарий говорит одно, а код делает другое:

```ruby
class Demo
  # @param [String] verbose Режим вывода
  # @param [String] count Сколько раз повторить
  # @return [String] Текст уведомления
  def notify(verbose:, count:)
    puts "verbose!" if verbose
    count.times { send_ping }
    count
  end
end
```

Комментарий говорит: обе строки, возвращается строка. А код делает другое:
`verbose` используется как флаг (значит Boolean), `count` — как число
(значит Integer), и возвращается тоже число. Придёт человек, прочитает коммент,
вызовет `notify(verbose: "false", count: "3")` — и получит аварию. Строка
`"false"` всегда истинна, а у строки `"3"` вообще нет метода `times`.
Цена гнили: рефакторинг вслепую, потому что доки врут.

### 2 минуты — что такое типы, зачем они нужны

Тип простыми словами: договор метода. Что принимает на вход, что возвращает,
какими ошибками падает. Нужно это трём потребителям: людям (понятная
документация), редакторам (подсказки, переходы, рефакторинг) и проверялкам
(ловить несоответствия до запуска). То есть типы — не только про поиск багов.

### 4 минуты — 🟢 спор с дядей Бобом: тесты вместо типов

Дядя Боб считает, что при полном покрытии тестами типы не нужны. Разбираем,
в чём разница: тесты показывают поведение на конкретных примерах, а типы
описывают договор сразу на все случаи. Плюс тесты не дают подсказок в редакторе
и нормальной документации из коробки. Вывод: это пара, а не замена друг другу.

### 4 минуты — 🟢 решение Мацумото: RBS отдельно от языка

Почему RBS живёт отдельной библиотекой, а не встроен в руби. Три причины
(подтверждены источниками — доклады Саутаро Мацумото, RubyKaigi 2020/2024):
не ломать синтаксис языка; оставить типизацию необязательной, чтобы не отпугнуть
тех, кто хочет динамический руби; для библиотек на Си внешний файл всё равно
нужен, потому что руби-кода там нет. Плюс rbs — это bundled gem: релизы выходят
чаще, чем релизы самого руби. Про то, что типы якобы пишут только разработчики
уровня middle и выше, — это моя трактовка этих решений, а не цитата Мацумото.
Так и сказать со сцены, чтобы не было вопросов.

### 4 минуты — 🟢 как типы уживаются в руби + ООП против типов

Коротко по инструментам: YARD — слой для людей, живёт в комментариях;
RBS + Steep — статическая проверка отдельно от кода; Sorbet — типы рядом
с кодом плюс проверки в рантайме; Prism — общий парсер, на котором теперь
строится тулчейн. Дальше утиная типизация на одном примере: если объект
отвечает на нужные методы (`to_s`, `each`), то он подходит — контракт задаётся
поведением. Отсюда разбор тезиса «в ООП тип берёт на себя имплементация»:
правда, но только пока договор никто не записал и не проверяет.

### 2 минуты — dry-стек как отдельный слой

Статика (RBS, Sorbet) проверяет код до запуска. А dry (`dry-types`,
`dry-struct`, `dry-validation`) — это договор во время работы: проверка данных
на границе системы. Пример на слайд:

```ruby
class User < Dry::Struct
  attribute :email, Types::String
  attribute :age, Types::Integer
end
```

Не тот тип пришёл — узнаешь сразу, а не глубоко внутри. Поэтому dry —
не конкурент Steep и Sorbet, а другой слой: они проверяют код, dry проверяет
данные.

### 2 минуты — карта библиотек, один слайд

Кто проверяет (Steep, Sorbet), кто генерирует сигнатуры из кода (sord, Tapioca,
rbs_rails, TypeProf), кто показывает доки (YARD, RDoc 8, Solargraph, Ruby LSP),
инфраструктура (готовые сигнатуры для гемов). Без экскурсии по каждому.
Про sord одной фразой: он конвертирует уже готовый YARD наружу в sig-файлы,
а docscribe наоборот создаёт сам YARD из кода.

### 7 минут — docscribe вживую (самый длинный блок)

Прогон по файлу: что было, команда, что стало. Файл с `rescue` — как появляются
описания ошибок (`@raise` и условный `@return`). Обновление типов из RBS
одной командой. Плагин, который берёт типы колонок из `db/schema.rb`
и дописывает их в модель (`t.boolean :is_admin` превращается в
`@!attribute [r] is_admin` с типом Boolean). В конце — как всё это вешается
на CI, чтобы гниль ловилась сама (ненулевой exit-код, ловля заглушек).

### 2 минуты — итоги и призыв

Начинать стоит с автогенерации и подсказок в редакторе, а строгость докручивать
потом, начиная с ядра. Поставить гем одной командой, проинициализировать,
попробовать на своём проекте, приносить правки. Примеры плагинов лежат
в репозитории.
